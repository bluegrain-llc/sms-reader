# Capacity and recovery release gate

Refs #10. Implementation provides repeatable checks; no 24-hour staging run, measured monthly cost, live bucket configuration, signing-key restore or cloud restore drill is claimed by this document.

## Capacity

Target: 100 owners, two registered phones each, 10,000 requests/day, 200 simultaneous streams for 30 minutes and 20 configured average streams over the full day. Keep scale-to-zero. Do not treat notification acceptance as delivery or human consent.

`node scripts/capacity-load.mjs --config /private/staging-load.json --output /private/capacity.json` runs 24 hours. `--quick` is a one-minute smoke, never full acceptance. Configuration requires `environment: "staging"`, `project`, different `productionProject`, exact Cloud Run `baseUrl`, `region`, `service`, and 200 `callers` entries containing owner and private bearer token (100 distinct owners, two approved caller grants each). Service must carry `environment=staging` label; runner verifies URL/project through gcloud. Use only disposable synthetic forms and credentials. It opens 200 streams initially (reconnect storm), schedules that peak for 30 minutes, then 17 streams for four hours and 16 for the rest of the day: 480 configured stream-hours, or 20 on average. The report separately measures admitted concurrency, actual stream-seconds, early EOFs and time observed at the peak; reconnect gaps are visible rather than counted as active streams. It creates and cancels synthetic forms at the required daily rate; it does not submit physical answers. Returned bodies and tokens are never logged. The private config is mode 0600 and outside Git. SIGINT/SIGTERM during the workload marks it interrupted even after the last request; completion also requires the whole observation window. A successful generator run is not capacity acceptance: streamProfileProven remains false pending independent telemetry checks; dispose fixture accounts using the deletion path after completion.

Collect Cloud Monitoring/Firestore usage deltas over the exact run, including all test instances, worker retries and event watchers. Export counters for compute vCPU-seconds, GiB-seconds, HTTP requests, Firestore reads/writes/deletes, storage GiB-month, storage operations, egress GiB, monitoring USD/month and backup USD/month. Capture dated primary unit-price sources; account for free tiers only when verified for the actual project. Run `python3 scripts/capacity-cost.py --measurements /private/measurements.json --output /private/cost.json`. Input requires `environment=staging`, `request_count=10000`, `duration_seconds=86400`, `average_streams=20`, `peak_streams=200`, `peak_seconds>=1800`, `pricing_date`, `pricing_sources`, `usage_evidence`, `usage` and `unit_prices` objects. Quantity keys are listed in the script; monetary monthly quantities use unit price 1. The calculator accepts usage deltas for exactly one 86,400-second measurement window with 10,000 requests; split longer experiments into daily windows. It rejects missing quantities and shorter or longer windows rather than pricing them as one day. Above $100/month blocks launch; billing alerts are notifications, not a hard spend cap. Staging experiment costs are separate from the monthly production target.

Fail acceptance on lost/duplicate accepted work, request failure, orphan watches, memory growth, owner starvation, or old delivery backlog. Confirm with telemetry and audit counts. Emulator tests exercise >250-item cursor pages and failed-item isolation; live callback/provider delays and backlogs >50/250/400 must also be exercised in staging before closure.

## Shared streams and maintenance

Each process shares one bounded 100-event tail and grant/account authorization watches per active grant. Existing cursors and durable paginated replay stay authoritative. Heartbeats use memory. Subscriber disconnect removes its subscription; final disconnect detaches all watches. Storage/watch errors, revoked/form-denied grants, account deletion and grant expiry close affected streams. Slow writers reconnect from their last received cursor. Distributed stream admission remains required across instances.

Maintenance cursors are persisted in `maintenancePages`. Scans order due work by due field plus document ID; account/revocation scans use document ID. Cursors advance past failed items and wrap to retry them without indefinitely blocking later owners. Individual jobs retain their own leases/idempotency. Multiple workers may inspect the same page; cursor updates use version checks and job transactions prevent double accepted outcomes. Cleanup queries due records and deletes an unchanged page in one conditional batch, using each snapshot's update time to reject concurrent renewal. A rejected batch falls back to individual conditional deletes with concurrency eight, so one changed or oversized record cannot block the other due records. A scheduled pass remains bounded; full backlog drain requires repeated passes/task wakeups. Monitoring backlog alerts are the external starvation signal.

## Independent security ledger

Set `SECURITY_LEDGER_BUCKET` before serving a recovery-capable production release. Missing configuration or unavailable GCS makes security-reducing mutations return failure before acknowledging their database mutation; health stays probeable. The ledger is in a separate recovery project, not the Firestore project. Runtime identity can create immutable objects and inspect retention but cannot delete/overwrite objects. No downloaded service-account key is required.

Authorize first; append intent before grant revocation, form-access denial, device pause/removal, webhook deletion and account deletion. Each create uses `ifGenerationMatch=0`; unconfirmed writes never acknowledge the mutation. A failed live transaction can leave an extra denial intent. Restore applies it conservatively rather than risking access restoration. Later re-enablement does not erase earlier deny intents; some access may need owner reapproval after a disaster. No SMS, answer or bearer token enters ledger intents.

`python3 scripts/recovery-provision.py --config /private/recovery.json --output /private/recovery-plan` renders exact command arrays and policies. Start from `recovery.example.json`; replacement values intentionally fail validation. Create dedicated backup and recovery identities first. Review every project, service identity, tested image digest and bucket. Provisioning does not run during build/deploy. `--apply --acknowledge-irreversible-ledger-lock` executes the reviewed plan; bucket retention locking is irreversible. Existing buckets/jobs require inspecting state and using update commands, not blind script reruns.

Both buckets enforce uniform access, public access prevention and default Cloud Storage encryption at rest. Snapshot lifecycle deletes after seven days. Ledger retention is locked for at least seven days and only intent objects expire; its source manifest remains. Disable soft delete for these buckets so retention is not silently extended. Snapshot expiry is lifecycle-managed and physical deletion is asynchronous. No whole-database PITR/export is enabled by this tooling. Source account deletion removes live data; isolated snapshots age out in seven days and ledger tombstones prevent their resurrection. Publish this retention before rollout.

Daily 03:00 UTC Scheduler OAuth invokes a Cloud Run backup job using the tested image digest. Backup identity has Firestore read access and snapshot create access; it cannot delete ledger objects. Monitor job failure and newest snapshot age (<24 hours). Runtime identity cannot read snapshot objects. Bucket access, manifests and locks must be verified in the cloud before claiming independent recovery readiness.

## Snapshot and disaster drill

Allowlisted metadata: account deletion flag; registered device identity, FCM routing and availability; caller identity/access expiry/revocation, forms permission and webhook signing configuration. Snapshots exclude request definitions, SMS codes, form answers, events, history, active request pointers, listener deadlines and runtime quotas. Snapshot objects contain private access metadata and webhook secrets and rely on encrypted storage plus IAM. Do not download them to Git, CI artifacts or ordinary logs.

Metadata RPO: 24 hours. Acknowledged deletion/revocation RPO: zero via the independent ledger. RTO: four hours after operator starts recovery; no 24/7 response promise.

1. Stop all old traffic, Scheduler/Tasks writers and enrollment; record incident time. Confirm no other region/revision can continue accepting mutations.
2. Select newest snapshot no older than 24 hours; verify source project, digest/checksum, manifest and locked ledger retention. Keep recovery accounts/objects independent of failed project. Missing coverage or inaccessible ledger blocks recovery.
3. Create an empty offline Firestore destination with required indexes/rules. Restore Firebase Auth project configuration/Google provider separately; Firestore restore does not restore Auth provider settings or user credentials. For same-project Firestore loss, existing Auth UIDs remain. For whole-project Auth loss, re-enroll users; never map metadata to newly generated UIDs without verified owner migration.
4. Run `node server/dist/recovery-cli.js restore --project SOURCE --destination-project DESTINATION --backup-bucket BACKUP --ledger-bucket LEDGER --snapshot OBJECT --acknowledge-empty-offline-destination`. Use scoped operator credentials. It immediately writes a serving block, validates source/coverage, replays all retained denials, clears stale state, restores allowlisted rows and removes deleted Firebase identities. Restored deleted accounts remain tombstoned; expired/legacy-manager grants remain revoked.
5. Any error leaves serving blocked. For a partial restore, keep traffic off, empty destination metadata using a separately reviewed operator action and restart from snapshot; CLI refuses a nonempty destination. Do not clear the block after a partial failure.
6. Verify count/checksum evidence, restored access, expiry, denied grants, denied forms, removed callbacks, paused/deleted devices, account tombstones and absence of request/code/answer/history data. Probe deleted cached credentials. Recheck final ledger listing after old writers are stopped; rerun restore if writer quiescence was not guaranteed.
7. Only after all checks pass, operator explicitly sets `recoveryControl/state.blocked=false`. Runtime watches fail closed before initialization and on watch errors. Restore never automatically reopens traffic. Record elapsed time and RPO source age, then run physical acceptance on a fresh request.

Record drill metadata only: source/destination project, snapshot object hash/name, timestamps, row/ledger counts, denied fixture outcomes and RTO. No codes, token values, full snapshots or private keys in evidence. Real recovery and cost gates remain open until this procedure is executed successfully.

## Signing and infrastructure backup

Use an encrypted offline/managed secret-vault backup for existing signing keystore, passwords, alias and future upload key. Keep two access-controlled copies outside repository/CI artifacts. Preserve signer continuity; a lost upload key can be reset through Play but loss of an externally managed app-signing key cannot be repaired by Firestore restore. Test restoration on an isolated machine by signing a synthetic APK and comparing certificate fingerprints without uploading keys.

Version infrastructure commands, schemas and artifact digests in Git. Back up scoped Firebase/OAuth/Play configuration, IAM bindings, Cloud Run/Scheduler/Tasks settings and certificate fingerprints privately; exclude service credentials and payload logs. Recreate against explicitly selected projects, deny client database access and verify required indexes/TTLs before traffic. Attach signed-artifact restore and infrastructure recreation drill metadata to #10; never claim success from this checklist alone.
