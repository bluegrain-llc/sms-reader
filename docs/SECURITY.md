# Security and reliability boundaries

## Interactive request boundaries

V2 requires a separate owner-approved form permission per connection; existing grants remain SMS-only. Request definitions stay immutable and submissions are validated against them. First-valid-submission transactions prevent competing phones from replacing answers. General form answers live separately for 24 hours; events and definitions expire seven days after termination. Metadata-only taps and foreground openings dedupe per device and do not imply agreement.

Polling, SSE and signed webhooks share one durable Firestore event log. Callback jobs and notifications are written with request mutations in transactions, leased by delivery workers and recovered by scheduled maintenance. Webhook delivery rejects non-public addresses on registration and each attempt, pins DNS to validated addresses, checks TLS certificates and never follows redirects. Only HTTPS port 443 is allowed. Webhook signing secrets are retained in server-only grants until removed or the account is deleted. Callback payloads contain events without answers. The [v2 contract](REQUEST_INBOX.md) defines signature verification, retention, permissions, and replay.


## Identity and authorization

The owner's Google identity is verified through Firebase ID tokens, including revocation checks. Management and phone routes require ownership. An agent grant is a random 256-bit bearer secret; only its SHA-256 digest is stored, as the grant ID. Grant metadata binds owner and stable caller identity permanently. A bot first receives a random pending credential; only its SHA-256 digest is stored, and no grant exists until an authenticated owner explicitly approves the paired connection. The credential stays only with that bot and is never in the verification link or phone UI. Approval atomically binds one owner and creates one grant; conflicting account claims cannot both win. Caller expiry/revocation and account/device availability are checked inside request transactions. Replacement connections cannot recover old results.

Comparison codes have 50 random bits, expire after ten minutes, and are protected by owner-authenticated lookup/decision quotas. The link opens a review screen, never an automatic approval. Client-supplied names/purposes are rendered as text and explicitly identified as requester-supplied. The owner must compare the code and recognize the connection they initiated. Public creation has persistent source/global limits and paced private polling. HTTPS App Links publish the registered Android certificate; a custom-scheme/code-entry fallback contains only the short-lived comparison code, not the credential.

Firestore transactions serialize the owner queue, caller/owner rate counters, per-phone readiness and consent, completion, cancellation, and revocation. One request is active per owner, with independent state for each participating phone. The first approved upload wins; losing phones never receive its code. Cancel/revoke/pause cannot revive a request. Revoking a grant immediately blocks completed-result reads even before physical cleanup. Pausing/removing a phone withdraws only that phone. Other participating phones and account-scoped caller grants remain available. Account-scoped history/results keep their normal retention until account deletion. Approved pairing metadata and code mappings are also removed during account deletion. Account deletion writes a tombstone first to prevent racing new registration or result writes, removes owned documents, then deletes the Firebase identity. Minimal account/device tombstones remain to prevent stale installation reuse or deletion races; account deletion removes its device tombstones too.

The server trusts the authenticated owner to run the official Android app. Firebase authentication proves identity, not that a particular system consent dialog was displayed. A modified owner-authenticated client could submit a code through the phone API. This v1 has no hardware/device attestation or cryptographic proof of system consent. Agent tokens have no ability to submit results, and Android-assisted filling accepts only candidates derived from an approved Activity Result. The owner can also type a code manually and explicitly tap Send. Phone submissions distinguish `android_consent` and `manual`; a ready, participating phone and an unexpired listening deadline are required. This source metadata is not attestation. For stronger assurance, separately design App Check/device attestation and enrollment proof; do not describe authentication alone as consent attestation.

## Message handling

No `READ_SMS`, `RECEIVE_SMS`, Contacts, default-SMS-handler, accessibility, or notification-listener permissions are requested. SMS User Consent's runtime receiver requires Google Play services' `SEND_PERMISSION`; the system dialog launches via Activity Result APIs from a visible activity. The notification tap targets that activity directly. When the app is backgrounded, the consent Intent stays only in ViewModel memory and a generic reopen notification is posted. The app never launches a background activity to display consent.

The full SMS is used only in memory after Android approval, immediately reduced to supported candidates, and never uploaded, persisted, saved in instance state, or logged. No analytics or crash-report SDK is installed. The app disables backups/transfers and screenshots; codes and plaintext token displays exist only in memory. Owner selection is mandatory when extraction returns multiple candidates; the selected code is submitted without a second Send tap. A single candidate is sent automatically after system approval. If multiple candidates exist, the owner chooses the code to send. Manual entry uses the same explicit Send action. Declining Android access leaves manual entry available; extraction cannot establish which site sent the SMS. Owners must review caller and purpose and the Android message dialog.

FCM dispatch uses a durable request outbox processed by the minute-by-minute maintenance job, with no fire-and-forget CPU dependency on Cloud Run. Notifications contain only opaque request IDs. Caller and purpose are fetched from authenticated phone endpoints. Stale, revoked, expired, or requests outside the phone activation snapshot cannot start a valid session. Notification retries use the same request ID and a persistent phone dedupe marker; FCM is at-least-once and a delivery acknowledgement can be lost, so transport-level exactly-once delivery is not claimed.

## Recovery and expiry

The phone persists only installation metadata, an in-flight request ID, and the previous listener's deadline. Process death ends the previous request explicitly when the app recovers. It never silently restarts a server-acknowledged listener. Because SMS User Consent has no cancellation API, a new session waits until the previous five-minute listening window has ended, including after denial/cancellation. The backend queues new requests while all available phones are still in earlier windows. Activation notifies all available registered phones; an individual phone still in cooldown can withdraw with `listener_failed` while another phone handles the request. The UI explains any remaining local wait. Screen rotation retains the receiver and consent Intent in the ViewModel. Network retries keep approved codes only in memory; killing the process loses the code and results in a new request requirement.

Code upload is retried with the same request binding; duplicate identical uploads are safe, and conflicting uploads fail. The server accepts results only after `awaiting_consent`, before the listening deadline, from that participating phone's own ready/awaiting-consent context. Completion/cancellation races have one terminal winner. An already completed result cannot be cancelled retrospectively; revoke its grant to block retrieval.

Results live in a separate Firestore collection with an exact two-minute API deadline and a TTL timestamp. The scheduled cleanup deletes due results without relying on TTL latency. Request and audit records never contain result codes. Retention here describes live application data. Optional metadata-only recovery tooling excludes codes, answers, definitions and history; its seven-day isolated snapshots and independent denial ledger require explicit provisioning and live verification before use. Whole-database PITR/exports are not enabled by that tooling. Operators must publish actual backup and log retention. See [recovery deployment and restore gates](recovery/README.md).

The service does not trigger OTP delivery, bypass sender restrictions, recover old SMS, read messages sent before readiness, or guarantee that offline/locked/background phones can complete consent. The physical acceptance checklist determines supported device behavior. Eligible sender/format and Google Play services availability remain platform constraints.


Retired manager-issuance APIs are removed and previously manager-issued credentials are rejected. The normal pairing/approval UI never displays a master secret or writes credentials to the clipboard. Legacy owner-created pilot credentials remain compatible. This direct pairing protocol is not a complete OAuth authorization server.

Bot-supplied short titles and Markdown explanations are bounded to 80 and 4,000 characters. CommonMark is parsed locally and rendered as native text; HTML is inert, no WebView is used, and links/images never fetch resources. The title and message never override the server-bound caller name.

Wizard definitions are immutable and declarative. Conditions reference only earlier fields. The server evaluates visibility independently and rejects hidden-branch answers. A final submission validates the whole selected path; step navigation does not upload values. Older phones are excluded from wizard delivery unless they advertise the supported wizard version.


Account deletion is an asynchronous durable job with immediate access tombstoning, bounded cleanup and Scheduler lease recovery. Read endpoints and SSE admission use shared Firestore limits. See [account deletion, receipts and deployment settings](ACCOUNT_DELETION.md) for contracts, current security review and remaining live acceptance.

## Version 3 service onboarding

[Onboarding](ONBOARDING.md) documents the separate registration/service/connection authorities and compact JWE delivery profile. A service token cannot call request/result APIs or impersonate an owner. New grants require explicit capability checks and an active parent service/operator. Disabling/deleting a service blocks associated recipient access immediately, including event feeds. Pending deliveries expire after seven days; retiring a compromised key invalidates its unacknowledged deliveries. Keep old delivery private keys during normal rotation and persist decrypted credentials before acknowledgement.

Public service names are operator supplied, without verification or endorsement. Public links carry no credentials. Opposite-party payloads omit emails/Firebase identities. Pairing permits requests; it never consents to responses. The relay processes submitted values, and an authorized agent receives those answers. Direct bearer MCP connections remain separate from the named-resource OAuth flow. Hosted OAuth uses PKCE S256, exact registered HTTPS redirects, public-address pinned client metadata retrieval, hashed opaque tokens, client/resource/grant capability bindings and newly issued static, non-expiring access/refresh credentials with explicit family revocation. Pre-update credentials retain their recorded expiry and TTL; [OAuth upgrade behavior](API.md#hosted-oauth-mcp) describes the legacy refresh exchange and required reconnection when no usable refresh credential remains. `OAUTH_CODE_KEY` is a private deployment secret used only to derive short-lived authorization responses across handoff. OAuth tokens and services are excluded from recovery snapshots and fail closed after restore. Provider live acceptance remains a release gate.
