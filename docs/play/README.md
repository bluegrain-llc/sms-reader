# Google Play release preparation

This package prepares a release; it does not publish one. Issue [#11](https://github.com/bluegrain-llc/sms-reader/issues/11) stays open until the actual Play-installed candidate and closed cohort pass. Prior pilot SMS results are historical evidence, not acceptance for a new candidate.

## Release order

1. Complete issues #5–#10, including physical phones, real cloud failure recovery, safe deployment, monitoring, deletion and disaster recovery.
2. Fill the private candidate record from `candidate.example.json`. Keep it in ignored `artifacts/play/`; never commit unpublished contacts, tester identities, credentials, signing keys or private evidence. The template includes only operator/contact details explicitly approved for public use.
3. Follow [signing and testing](release-checklist.md), review the [disclosure inventory](data-safety.md), and finish the [listing and reviewer package](listing.md).
4. Run `python3 scripts/check-play-release.py --record artifacts/play/candidate.json --output artifacts/play/readiness.json`. Supply `apksigner`, `aapt`, `jarsigner`, `keytool`, a JDK 17 or newer (`java`), and a read-only authenticated `gh` on PATH, plus a pinned `BUNDLETOOL_JAR`. Obtain bundletool from its [official releases](https://github.com/google/bundletool/releases) and verify the selected release's provenance. A successful report verifies local evidence integrity and gates; it is not proof that operator attestations are true. Review every referenced report separately.
5. Publish only after all blockers are cleared and the exact candidate has final green CI and five completed review/fix cycles. The tool has no upload, enrollment or publication operation.

`--offline` checks local records without querying GitHub or public URLs and always reports **not ready**. Exit 0 means readiness checks passed, 1 means blockers, 2 means invalid CLI input. Reports omit contact values, evidence contents, tool output and credentials. Required tool failures are blockers, never skipped passes.

Privacy and deletion URLs must use the canonical same-origin `/privacy` and `/account/delete` routes. The tool also rejects an HTTP 200 pilot privacy page without the supplied legal name/privacy email, and a deletion page without the configured confirmation flow. These read-only HTML checks do not prove Google popup sign-in, reauthentication or backend cleanup; their actual acceptance reports remain required. Support can use a separate HTTPS page.

## Candidate and evidence records

Artifact and evidence paths resolve relative to the candidate JSON directory. Include the installed base APK as `playApk` and **every** additional installed APK as `playSplits`; obtain the complete list from `adb shell pm path com.bluegrain.smsrelay` on the Play-installed test phone. An empty split list is valid only for a verified single-APK install. Keep the install-source and complete package inventory in `playInstalledSmoke` evidence. AAB structural checks cover all bundled native libraries; APK checks cover the delivered ZIP alignment and signers. The validator cannot independently prove installation source or the completeness of an operator-supplied APK list.

The validator also uses bundletool to inspect the uploaded AAB's base and additional module manifests. It rejects debuggable applications and the same prohibited permissions checked on the supplied APKs: `READ_SMS`, `RECEIVE_SMS`, `READ_CONTACTS`, `WRITE_CONTACTS`, `BIND_ACCESSIBILITY_SERVICE` and `BIND_NOTIFICATION_LISTENER_SERVICE`. APK and AAB checks use one prohibited-permission policy. A separately supplied clean Play APK cannot substitute for these AAB checks. The base application must explicitly disable backup and cleartext traffic, matching this app's manifest policy; additional modules cannot enable either setting. Resource references in these security flags cannot establish their disabled state and are rejected. Permission attributes must also be literal rather than unresolved resource references, including an application permission inherited by services. The gate rejects [bundletool resource-ID placeholders or unknown attribute names](https://github.com/google/bundletool/blob/1.18.3/src/main/java/com/android/tools/build/bundletool/xml/XmlProtoToXmlConverter.java#L147), rather than treating missing security-property names as safe. Before consuming that text dump, the checked-in `scripts/CheckBundleManifest.java` helper reads every module’s raw AAPT protobuf with the same supplied bundletool JAR. It verifies that every inspected Android attribute has its canonical resource ID, name and Android (or stripped) namespace; aliases and duplicate attributes fail closed. This avoids trusting names in a dump that omits resource IDs. Element checks use local names, including namespaced permission and application elements. Namespace-stripped named security attributes are checked conservatively, and simultaneous qualified/unqualified values are rejected. No dependencies are downloaded by the readiness command. The [bundle format](https://developer.android.com/guide/app-bundle/app-bundle-format) places each module's manifest under its own directory. These checks do not establish that the supplied APKs were generated from this AAB or replace Play-installed functional acceptance.

Each evidence reference has `path` and lowercase `sha256`. Its JSON must contain `result: "passed"`, the full candidate `commit`, `aabSha256`, `apkSha256` and ordered `splitSha256` list. Include the actual test/drill/approval report and timestamp, not only these envelope fields. The `physicalAcceptance` envelope additionally requires `packageName: "com.bluegrain.smsrelay"`; staging-package or missing package markers cannot establish production acceptance. `finalCiAndReviews` additionally contains `reviewCycles`, with at least five records containing full `head` SHA and `findingsAddressed: true`; keep each review/fix report alongside that record. These are operator attestations, not cryptographic attestations. Rebind only reports actually rerun or verified applicable to the final candidate. Live GitHub checks separately require prerequisite issues #5–#10 closed and the candidate's required check runs successful. Update the required CI name set deliberately if the repository renames its checks.

Required CI includes every `Android UI integration (API 26)`, `(API 33)` and `(API 36)` variant, together with server unit/type checks, backend integration, relay container smoke, Android unit/lint/build, staging callback-probe container and Play gate tests. All three UI variants must succeed; a skipped variant or the legacy single UI job cannot satisfy the gate. These are synthetic emulator checks, separate from carrier/FCM/system-consent acceptance on physical phones.

For `physicalAcceptance`, retain the original private record from `scripts/phone-acceptance.py` and require its `summary --require-pass` command to pass every case in [the current physical matrix](../PILOT.md). The recorder binds the operator-selected APK hash and backend project/region/revision and gathers physical-device/Play-services metadata; it does not prove that APK is installed. Independently verify the actual Play install/source/splits and bind applicable observations into the separate candidate evidence envelope. Preserve pending/blocked outcomes until actually exercised; hashed device identities and metadata reports remain private, with no codes, SMS bodies or screenshots of real data.

For `accountDeletion`, verify the current HTTP 202 acceptance followed by receipt-authenticated pending/running/completed status, interrupted-worker recovery, the same-account recent-login Android flow, and web popup sign-in/reauthentication. Receipt hashes expire after 24 hours; completed-job metadata after seven days; the account tombstone remains. The browser makes up to 120 status requests with a five-second delay after each response; network delays can extend polling beyond ten minutes. Cleanup continues if polling ends or the page closes. Never attach receipts, ID tokens or raw account data to reports. See [the actual contract](../ACCOUNT_DELETION.md).

For `capacityCostRestore`, include a `checks` object with every following field set to `true` only after its actual acceptance report exists: `capacityRun24Hours`, `monthlyCostWithin100Usd`, `isolatedMetadataBackup`, `lockedIndependentLedger`, `denialsReplayed`, `servingGateFailClosed`, `metadataRestoreDrill`, `signingRestoreDrill`, `infrastructureRestoreDrill`. These attestations bind the exact candidate like every other report; the validator does not execute cloud drills or measure costs. Follow the [capacity and recovery gate](../recovery/README.md): the full synthetic staging observation and measured monthly estimate, verified daily metadata snapshots and bucket policies, independent locked ledger, denial replay and explicit operator reopening after a successful offline restore. Verify metadata RPO at most 24 hours, acknowledged denial RPO zero, and RTO at most four hours after operator recovery starts. A rendered provisioning plan, quick load smoke or passed emulator suite cannot satisfy these live gates. Keep private snapshot contents, webhook secrets, tester identities and signing material out of evidence.

For `cloudAcceptance`, follow [staging cloud acceptance](../CLOUD_ACCEPTANCE.md) and retain the original private baseline report plus separate observations for every controlled fault drill. Add a `checks` object with `baseline`, `enqueue-recovery`, `worker-recovery`, `duplicate-delivery`, `provider-outage`, `storage-outage`, `interrupted-deletion` and `cleanup` all `true` only after their reports pass on the candidate's backend image. The harness deliberately leaves the five operator fault drills pending and exits incomplete; baseline success alone cannot satisfy this envelope. Preserve the original harness output rather than changing its `complete` field. The Play envelope binds reviewed baseline/drill reports to the candidate commit and APK/AAB hashes; it is a separate owner attestation, not the raw harness report. Verify the image/commit and tested `staging-callback-probe-container` artifact, signed public callback retries and actual timeout/disconnect, cross-revision replay, deletion completion and fixture cleanup. CI builds/tests the harness and probe; it does not perform live acceptance. FCM provider acceptance and authenticated synthetic manual submission do not establish physical notification display, carrier SMS or Android consent. No staging probe or fault-injection endpoint belongs in production.
