# Phone approval interface

The owner opens a code request while using their phone. They need a focused screen containing “Bot name — short title”, the requesting bot's Markdown explanation, a code input, Send and Cancel. This screen has no Admin navigation or device controls. Admin remains in the app's separate home area.

Focused-screen checkpoint: intent is to read the bot's explanation and deliberately send one code. Hierarchy puts the caller/title first, then the Markdown message, then a large monospace input and manual Send action. The existing paper, graphite, muted slate, teal and red palette is retained. Tonal surfaces separate the message from the inset input without shadows. Android sans uses 24sp semibold for the header and 16sp for the message; the code field uses 24sp monospace. Spacing follows the existing 4dp grid with 20dp outer padding and 12dp control gaps. The request-bound code field and request-bound code handoff are the signature. Dashboard tabs, auto-submit after reading, and a row of candidate Share buttons are replaced by focused reading, editable input and candidate selection that only fills the input.

The API accepts an optional short `title` and Markdown in `purpose`; integrations read local `.md` files and send their contents. Markdown is parsed locally with CommonMark and rendered as native text. HTML is inert; images and links do not fetch remote resources. Codes remain only in ViewModel memory. Manual entry requires Send. Android approval automatically sends a single extracted code. When several candidates exist, choosing one sends it without another tap. Declining Android access leaves manual entry available. Cancel still ends this phone's participation. Successful submission clears the input and closes the app. Other terminal outcomes provide Close.

Domain: listening window, caller identity, permission, handoff, expiry, private inbox. Color world: paper white, graphite text, muted slate labels, signal teal, amber waiting, red cancellation. Signature: the request-bound code field, bot-supplied explanation and automatic submission after Android approval. Avoid a dashboard of metrics, a chat imitation, and a giant unqualified “Approve” button.

Intent: keep the owner in control of the handoff. Hierarchy: caller and purpose lead the active request; time and cancellation remain visible. Palette: teal is reserved for readiness and the primary action; neutral paper surfaces let identity lead. Depth: tonal surface changes without shadows. Surfaces: paper background, lightly tinted grouped controls, slightly darker input containers. Typography: Android sans, 32/24/20/16/12sp hierarchy with weight for identities; monospace countdown and code candidates. Spacing: 4dp grid, 20dp panel padding, 12dp control gaps, 20dp section gaps, at least 48dp touch targets.

Relay is the home area. First sign-in plus notification permission registers the installation automatically. Opening a request shows only its dedicated SMS screen; Relay home shows phone availability when no request is open. Admin has Access, Devices, and History segments: review and approve a bot’s connection link/code; revoke individual app/bot access; pause/remove any registered phone; inspect metadata-only outcomes across all phones. The requesting bot supplies its name and purpose. Admin shows a comparison code and explicit Approve/Decline actions; the credential never appears on the phone. Code entry is a fallback when the link cannot be opened.

Use Material 3 Compose controls for semantics, dialogs, tabs, segmented buttons, and button feedback. Disable conflicting mutations while running, keep local Stop available during upload, show empty/loading/error states, support font scaling, and open incoming requests in the dedicated SMS screen. Device removal and caller revocation explain their different scopes before confirmation. “Handled on another phone” is a final outcome without showing its approved code.
