# Provider adapters

`connectProviderTools` reads one selected recipient connection from private CLI storage, connects to `/mcp`, and produces function declarations for OpenAI, Anthropic, Google, xAI Responses and Microsoft Azure OpenAI Responses. No credential is returned in those declarations. Registration, service management and delivery consumption run in software outside the model tool loop. Configure the model provider's SDK separately; these adapters make no inference calls and print no responses.

```js
import { connectProviderTools } from './integrations/providers.mjs';
const relay = await connectProviderTools({ profile: 'my-agent', connectionId: selectedConnectionId });
// Pass relay.openai, relay.anthropic, relay.google, relay.xai, or relay.microsoft to the provider's tool interface.
// Execute a provider-selected function with relay.execute(name, args).
// Send only that authorized result back to the model, then close on shutdown.
```

OpenAI and xAI Responses use function tools; Anthropic Messages uses tools with `input_schema`; Google GenerateContent uses `functionDeclarations` with `parametersJsonSchema`. Preserve provider tool-call IDs when returning the result, according to the provider's SDK. The relay server rechecks permissions on every call. The SDK convenience clients also provide direct REST request/result/event methods.

The shapes follow the [OpenAI tool and MCP guide](https://developers.openai.com/api/docs/guides/tools-connectors-mcp), [Anthropic MCP connector guide](https://platform.claude.com/docs/en/agents-and-tools/mcp-connector), and [Google function calling guide](https://aistudio.google.com/docs/function-calling). Test each provider's live authorization and function-calling flow before publishing an integration release. The automated profiles in `contracts/provider-authorization.json` exercise ChatGPT DCR/CIMD, Claude hosted DCR, the Messages OAuth-bearer path, xAI Responses and Microsoft Azure OpenAI Responses application-managed OAuth bearer and Gemini Apps persistent linking against both backends, including discovery, exact callbacks, PKCE, scope narrowing, refresh and revocation. OpenAI tools publish explicit OAuth schemes and return its documented linking challenge. CIMD fixtures enter through validated registration and the shared cache; these tests do not fetch actual provider documents, navigate callbacks, register with providers or send inference requests. Redirect-host validation can perform public DNS resolution.

These are developer integrations. Hosted connections use the separate OAuth endpoints described below; a direct `smsr_` bearer connection is not an OAuth implementation. See the [xAI integration and acceptance boundaries](XAI.md) and [Microsoft Azure OpenAI integration and acceptance boundaries](MICROSOFT.md). The [AWS Bedrock Converse adapter](AWS.md) provides client-side tool declarations and result dispatch over the same authorized private connection.

## Hosted connections

Register the integration’s named service with the CLI, then run `relay service hosted-link --profile NAME`. Configure that public named-service URL as the provider’s remote MCP endpoint. Discovery, dynamic/client-metadata registration, Google/Firebase sign-in, one explicit Connect confirmation, PKCE and static credentials then use the relay server. Keep provider-managed OAuth tokens outside model arguments and prompts. No recipient credentials or delivery private keys are part of the provider’s model configuration.

For an API application that manages the OAuth flow in software, `hostedProviderConfig('openai', {resource, accessToken})` returns the remote MCP configuration for the Responses API's `tools` array. `hostedProviderConfig('anthropic', {resource, accessToken})` returns the `mcp_servers`, `tools` and beta settings for the Messages API. `resource` is the named-service HTTPS URL, and `accessToken` is its OAuth access token. Keep the returned configuration private in application software; it contains authentication fields and must never be printed or returned by a model tool. The helper rejects direct pairing/service credentials and legacy MCP URLs. It sends no inference requests.

- **OpenAI:** use an authenticated remote MCP app/connector with the returned URL. The server publishes authorization-server and protected-resource discovery, PKCE S256 and a DCR endpoint. Follow the [official hosted authentication requirements](https://developers.openai.com/plugins/build/auth).
- **Anthropic:** configure the named endpoint in the hosted remote MCP connection. For API integrations, obtain the connection token through OAuth in application software and pass it through the connector’s authentication setting, following the [official MCP connector guide](https://platform.claude.com/docs/en/agents-and-tools/mcp-connector).
- **Google:** configure the named-service HTTPS endpoint in Gemini Apps. The OAuth profile checks discovery, callback binding, PKCE, static credentials and explicit revocation against both backends. Newly issued access and refresh credentials stay unchanged on refresh and have no automatic expiry; pre-update credentials follow the [OAuth upgrade behavior](../docs/API.md#hosted-oauth-mcp). Live hosted acceptance, Connected Console enrollment and publication remain external steps.

- **xAI Responses API:** application software obtains an OAuth access token and passes `hostedProviderConfig('xai', {resource, accessToken})` in the Responses `tools` array. The [remote MCP guide](https://docs.x.ai/developers/tools/remote-mcp) documents the authorization field; xAI does not perform the application's OAuth flow here. The synthetic application-owned callback in the authorization fixture is not an xAI callback or an assertion of Grok consumer-app support. See [setup and pending live acceptance](XAI.md).

- **Microsoft Azure OpenAI Responses API:** `relay.microsoft` supplies local function declarations; `hostedProviderConfig('microsoft', {resource, accessToken})` supplies private remote MCP configuration using `headers.Authorization` and explicit tool approval. Application software completes OAuth with its own callback. See [setup, supported surface and pending acceptance](MICROSOFT.md).

Use `forms` unless SMS is needed; the service must have declared SMS before approval can include it. The approval screen shows the configured service and requesting client, and the user can narrow the displayed permissions. A phone handoff QR contains a public consent-session URL. The original browser waits for the same signed-in owner’s approval. Test sign-in, resource discovery, cancellation, refresh, narrow scopes and disconnection in each provider before release. No provider registration, inference traffic or marketplace submission has been performed by the repository tests.
